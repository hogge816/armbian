Executive conclusion
--------------------
The running device is a Hinlink HT2 based on Rockchip RK3528A. It is not
possible to treat HT2 and X88Pro-13 as two independently validated DTB targets
on this machine:

1. /boot/dtb/rockchip/rk3528-hinlink-ht2.dtb and
   /boot/dtb/rockchip/rk3528-x88pro13.dtb are byte-for-byte identical.
   Both contain model "Hinlink HT2" and compatible
   "hinlink,ht2", "rockchip,rk3528".

2. The running Linux FDT has HT2 identity and RK3528A compatibility:
   model "Hinlink HT2"
   compatible "hinlink,ht2", "rockchip,rk3528a"

3. The machine's currently booting raw startup chain is a hybrid chain:
   - RKNS first-stage idblock at user-area sector 64, byte offset 32768.
   - FIT/U-Boot package at user-area sector 16384, byte offset 8388608.
   - The first-stage idblock is byte-for-byte identical to the repository's
     config/boards/rockchip-rk3528-fastyumjin/idbloader.img.
   - The FIT's embedded U-Boot FDT is byte-for-byte identical to the repository's
     config/boards/rockchip-rk3528-fastyumjin/u-boot-h28k.dtb.
   - The FIT configuration description is rk3528-hinlink-h28k.
   - The Linux-stage FDT is HT2/Fastyumjin content and is passed to Linux after
     U-Boot/boot.scr handling.

4. Therefore the current known-good boot path is not a pure, separately built
   HT2 chain. It uses the repository's Fastyumjin/H28K-named bootloader pieces
   together with the HT2 Linux-stage device tree.

5. The repository's RK3528 workflow is internally inconsistent for this device:
   it builds BOARD=rockchip-rk3528-fastyumjin, validates a FIT description
   rk3528-hinlink-h28k, uses u-boot-h28k.dtb, and does not build BOARD=hinlink-ht2.

6. The repository's workflow named build-oec-turbo-6.18.yml is for RK3566,
   not RK3528. The repository does contain rockchip64-6.18 patch and DTS
   material, including rk3528-fastyumjin.dts, but there is no evidence in the
   inspected workflow that it is a ready-to-run HT2 6.18 workflow.

Evidence of likely boot failure class
--------------------------------------
The device currently reaches Linux with the same raw idblock and H28K U-Boot
FDT that the repository workflow calls known-good. Thus the following are
not the most likely first causes for an ordinary Linux boot failure on this
machine:
  - RK3528 DDR initialization in the current idblock;
  - basic eMMC raw offsets used by the current chain;
  - basic Linux-stage HT2 identity;
  - basic HDMI/GMAC/eMMC hardware availability.

High-risk differences in external HT2/X88Pro images are instead likely to be:
  - replacing the RKNS idblock with a board-mismatched DDR blob;
  - replacing the H28K U-Boot FIT FDT or its ATF/BL31 combination;
  - changing the 8 MiB FIT location or GPT/raw boot offsets;
  - using an unverified X88Pro name for a duplicated HT2 DTB;
  - using an unpatched upstream/mainline RK3528 DTS against the vendor U-Boot
    and vendor kernel ABI;
  - changing U-Boot FIT configuration/verification or Android/RKNS packaging.

These are ranked hypotheses, not direct proof of the contents of each external
firmware image, because those external images were not supplied for hashing.

--------------------------------
The running system emits these warnings/errors:

  - OTG PHY supply and vbus-supply properties are absent
  - HDMI avdd-0v9/avdd-1v8 supply properties are absent
  - display subsystem: failed to parse loader memory
  - GMAC eth_lpi IRQ absent
  - GMAC phy supply absent; dummy regulator used
  - GMAC rx_delay absent; driver sets 0xffffffff
  - GMAC mac_clk_rx/mac_clk_tx/clk_mac_speed absent
  - dwmmc reports missing normal/idle pinctrl states for some controllers

The same live system nevertheless probes eMMC, HDMI, GMAC and Linux successfully.
These messages are compatibility risks for future kernel/U-Boot changes, not a
proven explanation for the pre-Linux boot failures.

What is proven vs not proven
----------------------------
Proven:
  - Hardware identity is Hinlink HT2 / RK3528A.
  - Current HT2 and X88Pro DTB files are identical aliases.
  - Current eMMC user-area sector 64 exactly contains the repository idbloader.
  - Current eMMC user-area sector 16384 contains an H28K-described FIT.
  - Current FIT FDT exactly matches repository u-boot-h28k.dtb.
  - Current Linux reaches userspace with an HT2/RK3528A runtime FDT.
  - Repository 6.18 workflow shown in the audit is RK3566, not RK3528.

Not proven without external files or serial capture during a failed boot:
  - Which exact stage failed in the previously downloaded external images.
  - Whether the physical reset button is electrically connected to the RK3528
    SARADC/recovery path.
  - Which physical USB connector is connected to the RK3528 OTG-capable port.
  - Whether a failed external image changed DDR firmware, BL31, FIT, DTB, raw
    offsets, or all of them.

Required implementation gates
-----------------------------
Before any repository modification or 6.18 build for this machine:

1. Preserve the current raw chain as reference artifacts:
   idbloader SHA256 ee4ea8d45f9ae9c70dc9ea0c8d3f3acc93063f9d078902940c811ce670672af3
   U-Boot FDT SHA256 db83a0738a78c82a0c5e5913509555359900fe2075497362dabc7ad2e4a3decc
   raw locations: sector 64 and sector 16384.

2. Build a new SD-only test image first. Do not write eMMC.

3. Keep the current idbloader and FIT packaging unchanged in the first test.
   Change only Linux kernel/rootfs and the Linux-stage DTB after proving the
   image packaging remains identical at the raw boot offsets.

4. Use a new explicit HT2 board target or a carefully scoped derivative of the
   Fastyumjin target. Do not call a H28K/Fastyumjin bootloader output an HT2
   image without recording that it is the same mixed chain as the running host.

5. Do not use build-oec-turbo-6.18.yml for this device.

6. For 6.18, verify that the build actually applies the RK3528 DTS and patches,
   then inspect the generated image's idblock, FIT description, embedded U-Boot
   FDT, Linux DTB and raw offsets before any hardware test.

7. Capture a serial log at 1500000 baud for any SD test. A no-display failure
   must be classified by the last visible stage: BootROM/DDR, U-Boot, kernel
   earlycon, or rootfs.

8. Do not short eMMC pins or write boot0/boot1 based only on this report.
